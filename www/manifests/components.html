# Accessibility

## What's it all about?

In today's digital age, ensuring that web applications are accessible to everyone is not just a legal requirement but a moral imperative.
Accessibility in web development means designing and building websites and applications that can be used by people of all abilities and disabilities.
This includes individuals with visual, auditory, motor, and cognitive impairments.

## Why accessibility matters?

**Inclusivity**: Accessibility ensures that everyone, regardless of their abilities, can access and use our web applications.
This inclusivity fosters a more diverse and equitable digital environment.

**Legal compliance**: Many countries have laws and regulations that require digital content to be accessible.
Non-compliance can lead to legal repercussions and damage to the company's reputation.

**Enhanced user experience**: Accessible design often leads to a better overall user experience.
Features like keyboard navigation, contrast, readable text benefit all users, not just those with disabilities.

**Market reach**: By making our web applications accessible, we can reach a broader audience, including the millions of people with disabilities worldwide.

## Accessibility in design systems
A design system is a collection of reusable components and guidelines that ensure consistency and efficiency in design and development.
Just like our base library and role model [Shoelace](https://shoelace.style/resources/accessibility) we promise to build each component with accessibility in mind.

### Key aspects
**Component-level accessibility**: Each component in our design system is built to be accessible.
This includes ensuring proper color contrast, keyboard navigability and screen reader compatibility.

**Holistic approach**: While component-level accessibility is crucial, it's not the whole picture.
Accessibility must be integrated into the entire application. This means considering the user journey,
ensuring that all interactions are accessible, and testing the application with real users who have disabilities.

**Progressive approach**: Accessibility is not a binary (yes/no) and not a one-time task either but an ongoing process.
We strive to making Synergy as accessibility as possible and improve it continuously.
As Synergy evolves, we continuously test and improve our components to meet the latest accessibility standards and best practices.

## Our commitment to accessibility
We are committed to making Synergy components accessible to everyone, so we decided to make it part of our Definition-of-Done.
Synergy is always developed with accessibility in mind, ensuring that every component is usable by all users.
We believe that accessibility is a fundamental aspect of good design and are dedicated to continuously improving our practices to create a more inclusive digital world.

# Overriding global default settings for components

Most Synergy components provide a way to configure their appearance and behavior through a set of properties.
However, it can be cumbersome to set the same properties for all components in your application.

Therefore, Synergy includes a low level API that allows you to set global defaults for the rendered components.
This can be used to set the default size or other global settings that should be applied to all rendered components.

## Setting global defaults

The settings can be set on a global or component level via `setGlobalDefaultSettings` and `setDefaultSettingsForElement` respectively.

> ⚠️ The configured defaults are applied to all components rendered **after** the new configuration has been set.
> This means in most cases it is crucial to call `setGlobalDefaultSettings` or `setDefaultSettingsForElement` **before rendering any components**.

### `setGlobalDefaultSettings` (recommended)

To set global defaults for all components, you can use the `setGlobalDefaultSettings` function exported from `@synergy-design-system/components`.
This function accepts an object with the settings you want to apply to the components.

> You may provide a partial object with only the settings you want to override to leave the rest of the settings intact.

```typescript
import { setGlobalDefaultSettings } from '@synergy-design-system/components';

// Sets the size for SynButtons and SynInputs to small and large respectively
setGlobalDefaultSettings({
  size: {
    SynButton: 'small',
    SynInput: 'large',
  }
});
```

### `setDefaultSettingsForElement`

You can also set defaults scoped for a specific component using the `setDefaultSettingsForElement` function.
This works in the reverse way of `setGlobalDefaultSettings` and allows you to set defaults for a specific component.

```typescript
import { setDefaultSettingsForElement } from '@synergy-design-system/components';

// Sets the size to small and variant to filled for all newly rendered SynButton components
setDefaultSettingsForElement<SynButton>('SynButton', {
  size: 'small',
  variant: 'filled',
});
```

### `resetGlobalDefaultSettings`

You may use `resetGlobalDefaultSettings` to reset the global default settings to their initial state.
This will also automatically emit an event to notify all components that the settings have changed.

```typescript
import { resetGlobalDefaultSettings } from '@synergy-design-system/components';

resetGlobalDefaultSettings();
```

## Live update via events

When event support is enabled and either `setGlobalDefaultSettings` or `setDefaultSettingsForElement` are called, a `syn-default-settings-changed` event is dispatched to notify all components that the settings have changed.
This feature may for example be used to implement a layout switcher (e.g. to switch between various sizes in an application).
Please have a [look at our demo projects](https://github.com/synergy-design-system/synergy-design-system/tree/main/packages/_private) for further information.

If the component was initially rendered with the default setting of the corresponding attribute, it will be updated to the new setting.
**However**, if it was rendered with a custom value, it will not be updated!

If the element was rendered before the event support was enabled, it will also not be updated!
You will have to make sure to call `enableSettingEmitEvents` before the initial render to ensure that all components are listening for the event.

You may also listen to the event to react to changes in the default settings.

```typescript
import {
  enableSettingEmitEvents,
  type SynDefaultSettingsChangedEvent
} from '@synergy-design-system/components';

// Don´t forget to enable the feature
enableSettingEmitEvents(true);

window.addEventListener('syn-default-settings-changed', (event: SynDefaultSettingsChangedEvent) => {
  console.log('Default settings changed', event.detail);
});
```

    {Object
      .values(INITIAL_DEFAULT_SETTINGS)
      .map(setting => Object.keys(setting))
      .flat()
      .filter((value, index, self) => self.indexOf(value) === index)
      .sort()
      .map(c => {
        const settings = extractDefaultSettingsForElement(c);
        const componentName = snakeCase(c, {
          delimiter: '-',
        });

        // Build the examples
        const exampleCalls = Object
          .entries(settings)
          .map(([key, value]) => `
  ${key}: {
    ${c}: ${typeof value === 'object' ? JSON.stringify(value, null, 2) : `'${value}'`},
  }
          `.trim())
        const example = `setGlobalDefaultSettings({
  ${exampleCalls.join(',\n  ')}
});`.trim();

        return (
          <tr key={`${c}--details`}>
            <td><code>{`<${componentName}>`}</code></td>
            <td>{c}</td>
            <td>
              {Object
                .entries(settings)
                .sort(([a], [b]) => a.localeCompare(b))
                .map(([key, value]) => (
                  <>
                    <strong key={`${c}--${key}--key`}>{key}</strong>:
                    {' '}{typeof value === 'object' ? JSON.stringify(value, null, 2) : value}
                    <br />
                  </>
                ))
              }
            </td>
            <td>
              <code>{example}</code>
            </td>
          </tr>
        );
    })}
  </tbody>
</table>

# Localizing Synergy components

Components can be localized by importing the appropriate translation file and setting the desired [`lang`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/lang) attribute and/or [`dir`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/dir) attribute on the `<html>` element.
Changing the lang attribute will automatically update all localized components to use the new locale.

> Synergy provides a localization mechanism for component internals.
> This is **not** designed to be used as localization tool for your entire application.
> You should use a more appropriate tool if you need to localize content in your app.

## Static examples

Here’s an example that renders Synergy components in Spanish, using plain html.

```html
<html lang="es">
  <head>
    <script type="module" src="/path/to/synergy/dist/translations/es.js"></script>
  </head>
  <body>...</body>
</html>
```

```html
<html>
  <body>...</body>
  <script type="module">
    // Alternative usage via Javascript.
    // Same as setting <html lang="es">
    import '@synergy-design-system/components/translations/es.js';
    document.documentElement.lang = 'es';
  </script>
</html>
```

## Translation resolution

The locale set by `<html lang="...">` is the default locale for the document.
If a country code is provided, e.g. `es-PE` for Peruvian Spanish, the localization library will resolve it like this:

1. Look for `es-PE`
2. Look for `es`
3. Fall back to `en`

Synergy uses English as a fallback to provide a better experience than rendering nothing or throwing an error.

## Multiple locales per page

You can use a different locale for an individual component by setting its `lang` and/or `dir` attributes.
Here is a contrived example to demonstrate.

```html
<html lang="es">
  <body>
    <syn-button><!-- Spanish --></syn-button>
    <syn-button lang="ru"><!-- Russian --></syn-button>
  </body>
</html>
```

For performance reasons, the `lang` and `dir` attributes must be on the component itself, not on an ancestor element.
This limitation exists because there’s no efficient way to determine the current locale of a given element in a DOM tree.

```html
<html lang="es">
  <body>
    <div lang="ru">
      <syn-button><!-- still in Spanish --></syn-button>
    </div>
  </body>
</html>
```

## Available localizations

Synergy ships with a number of translations.
The default is English (US), which also serves as the fallback locale.
As such, you do not need to import the English translation.
To see a list of all available translations in the latest version, [refer to this directory](https://github.com/synergy-design-system/synergy-design-system/tree/main/packages/components/src/translations).

You do not need to load translations up front.
You can import them dynamically even after updating the `lang` attribute.
Once a translation is registered, localized components will update automatically.

# Browser Support

Synergy is designed to work across a wide range of browsers, ensuring that our components are accessible and functional for as many users as possible.
To achieve this, we define a set of browser baselines that specify the minimum versions of browsers that Synergy supports.

They are created based on `baseline widely available` and fixed during the first release of a major Synergy version. This means that the browser baselines for a given Synergy version will not change until the next major release, even if there are updates to browser usage or new versions of browsers are released.

> Synergies baselines are usually updated once for each new major Synergy release to reflect changes in browser usage and to ensure that we are providing the best possible experience for our users.
